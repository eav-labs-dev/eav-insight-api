# EAV Insight API — Database Notes

## Purpose

The database foundation models the first production-style business workflow for EAV Insight: organizations, users, reports, documents, and tags.

This gives the project a real backend domain model instead of only a framework skeleton.

## Core Tables

| Table | Purpose |
|---|---|
| `organizations` | Business workspace or client account |
| `users` | User records scoped to an organization, including password hash storage |
| `reports` | Operational reports and searchable business records |
| `documents` | Files attached to organizations and reports |
| `tags` | Organization-specific labels for reports |
| `report_tags` | Many-to-many relationship between reports and tags |

## Relationship Overview

```text
Organization
  ├── Users
  ├── Reports
  │     ├── Documents
  │     └── Tags through report_tags
  ├── Documents
  └── Tags
```

## Migration Commands

Start PostgreSQL:

```bash
docker compose up -d db
```

Run migrations:

```bash
alembic upgrade head
```

Rollback the latest migration:

```bash
alembic downgrade -1
```

Create a new autogenerated migration after model changes:

```bash
alembic revision --autogenerate -m "describe change"
```

## Seed Demo Data

After running migrations, seed local demo data:

```bash
python scripts/seed_demo_data.py
```

Or use the Makefile:

```bash
make db-upgrade
make seed
```

## Design Notes

- Primary keys use UUID strings for portability across SQLite tests and PostgreSQL development.
- Organization scoping is included from the start to support realistic multi-tenant workflows.
- Report status is currently stored as a string to keep the first migration simple and portable.
- Tags are unique per organization by `organization_id` and `slug`.
- Documents can exist at the organization level and may optionally link to a report.


## Authentication Storage

The `users` table now includes `password_hash` for storing salted password hashes. Plaintext passwords must never be committed, logged, stored, or returned from API responses.

The demo seed user uses a local-only password documented in the seed script and should not be treated as a production credential.
